# 应用部署目录规范（通用模板）

> 适用：所有自研/自建后端服务（Docker 部署）+ 可选前端（Nginx 静态托管）。  
> 目标：每个应用"代码、数据、日志、镜像、前端"统一收敛到一个应用根目录下，整目录可备份、可迁移，且与宝塔面板 /www 解耦。  
> 当前以服务器 `121.40.42.131`（Alibaba Cloud Linux 4）为基准环境。

---

## 1. 统一目录结构（模板）

每个应用独占一个 `/opt/<app>/` 根目录，`<app>` 用小写中划线命名（如 `dingchi-new-api`、`weekly-menu`）。

```
/opt/<app>/
├── backend/          # 后端代码：docker-compose.yml / .env / Dockerfile / 源码
├── frontend/dist/    # 前端静态产物（Nginx root），不放入宝塔 /www/wwwroot
├── docker-images/    # 后端镜像 tar 备份（docker save 导出），用于离线迁移/回滚
├── data/             # 应用数据（挂载到容器 /data 等）：上传文件 / 证书 / SQLite
└── logs/             # 应用日志（挂载到容器 /app/logs 等）
```



---

## 2. 命名与落位规则

| 项       | 规则                                                                                          |
| ------- | ------------------------------------------------------------------------------------------- |
| 应用根     | `/opt/<app>/`，`<app>` 全小写、中划线分隔                                                             |
| 后端代码    | 必须放在 `backend/`，compose / 源码 / Dockerfile 全在此目录内；执行 `docker compose` 时 `cd backend/`        |
| 前端产物    | 本地 `bun` / `npm run build` 出 `dist` → 仅传 `dist/` 到 `frontend/dist/`，由**独立 Nginx server** 托管 |
| 前端禁区    | **绝不混进** `/www/wwwroot`（那是宝塔专属，避免被面板误操作）                                                    |
| 数据 / 日志 | compose 的 `volumes` 用**绝对路径**指向应用根下的 `data/`、`logs/`，避免"在哪执行 compose"的路径歧义                  |

---

## 3. 数据库 / 中间件访问约定

- 服务器本地已装的 MySQL / Redis，后端容器经 `network_mode: "host"` + `127.0.0.1:3306` / `127.0.0.1:6379` 直连（无需服务监听 `0.0.0.0`，更安全）。
- 连接串里的 `@` / `#` 等特殊字符**必须 URL 编码**（`%40` / `%23`），否则 DSN 会被截断。
- 部署前确认：MySQL / Redis 已安装并启动；目标库已手动 `CREATE DATABASE`；账号密码正确。
- 安全组只放行必要端口，MySQL / Redis 不长期对全网开放。

---

## 4. 前端（Nginx）约定

- 前端 axios `baseURL` 为空（相对路径 `/api/...`）→ Nginx 反代 `/api` 到后端即可，无 CORS、无需改前端代码。
- Nginx `root` 指 `frontend/dist`；反代 `127.0.0.1:<backend-port>` 覆盖 `/api`、`/v1`、`/mj`、`/oauth`、`/verification` 等；SSE 接口不缓冲；SPA 404 回落 `index.html`。
- 后端容器端口只绑 `127.0.0.1`（由 Nginx 反代，不直接暴露公网）。

---

## 5. 镜像与构建约定

- 后端一律**从源码构建**（`docker compose up -d --build`），不用他人预构建镜像（否则本地改动不生效）。
- Dockerfile 优化：前端若拆给 Nginx，后端 Dockerfile 删除 bun 构建阶段，仅 `go build` + BuildKit 缓存挂载（`--mount=type=cache,target=/root/.cache/go-build`），增量构建数十秒级。
- 每次成功构建后留档：

```bash
docker save <image>:<tag> -o /opt/<app>/docker-images/<app>-<tag>-$(date +%Y%m%d).tar
```

---

## 6. 配置与密钥

- 敏感配置（SQL_DSN / REDIS_CONN_STRING / SESSION_SECRET）放 `backend/.env`，加入 `.gitignore`，**不提交**。
- SESSION_SECRET 等用随机长串：`python -c "import secrets;print(secrets.token_hex(32))"`。

---

## 7. 备份 / 恢复

- 备份：`rsync -a /opt/<app>/ 备份机:/backup/<app>/`（`docker-images/` 大文件可单独策略或随盘快照）。
- 回滚：加载 `docker-images/*.tar` 后 `docker compose up -d`。

---

## 8. 部署前检查清单（Checklist）

- [ ] 服务器磁盘：是否单盘？有独立数据盘则把 `data/` `logs/` 指向数据盘挂载点
- [ ] 建目录：`mkdir -p /opt/<app>/{backend,frontend/dist,docker-images,data,logs}`
- [ ] MySQL / Redis 已装已启动；目标库已建；密码正确
- [ ] 后端源码 rsync 到 `backend/`；前端 `dist` 到 `frontend/dist/`
- [ ] `backend/.env` 填真实连接串（特殊字符已编码）
- [ ] `cd backend && docker compose up -d --build`，随后 `docker save` 备份镜像
- [ ] Nginx 配反代 + `root` 指 `frontend/dist`，`nginx -s reload`
- [ ] 访问接口 / 面板验证连通

## 9. 实例对照（dingchi-new-api）

| 模板项        | 实际值                                          |
| ---------- | -------------------------------------------- |
| `<app>`    | `dingchi-new-api`                            |
| 后端根        | `/opt/dingchi-new-api/backend/`              |
| 前端根        | `/opt/dingchi-new-api/frontend/dist/`        |
| 数据         | `/opt/dingchi-new-api/data` → 容器 `/data`     |
| 日志         | `/opt/dingchi-new-api/logs` → 容器 `/app/logs` |
| 镜像备份       | `/opt/dingchi-new-api/docker-images/`        |
| DB / Redis | `127.0.0.1`（host 网络直连）                       |

## 10. 备注（基于 121.40.42.131 实测）

- 该机 `lsblk` 仅一块 `vda`（400G），所有路径（`/opt`、`/var`、`/www`）均挂在 `/dev/vda3`，**无独立数据盘**。故"系统盘 vs 数据盘"在本机不成立；如需真正隔离数据，去云控制台挂云盘到 `/data` 再迁移。
- 宝塔面板：`https://121.40.42.131:8888/<安全入口>`（安全入口路径随机、不可省略）；进面板装 MySQL / Redis 并确认监听与密码。
- MySQL root 密码与 Redis 密码是两套，**不能混用**（实测 `Dingchi@2026#` 是 Redis 的，连 MySQL root 报 `1045 Access denied`）。
